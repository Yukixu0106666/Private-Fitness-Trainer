# Fitness Agent

English | [中文](README.md)

Fitness Agent is a bilingual, memory-aware AI fitness coach built around three natural check-in points: morning readiness, post-workout activity, and evening nutrition and digestion. Rather than relying on weight alone or asking users to complete one large form at the end of the day, it turns structured daily records into grounded plans, recovery suggestions, and next-day reviews.

It is not intended to replace a human coach. It is a practical assistant that remembers what happened, uses the evidence available, and clearly acknowledges missing information.

## How it works

In the morning, users record their weight, sleep, energy, muscle soreness, and available time. The coach uses that information to suggest meals and exercise for the day.

After training, users log each exercise and its actual duration, then indicate whether they followed the morning plan. Stretching suggestions are based on the muscle groups actually trained instead of a fixed routine.

In the evening, users add meals, food photos, and digestion information. On the following morning, the coach reviews the completed day, plan adherence, and recent trends, then provides a score from 0 to 100 with a short explanation.

The score is generated by the configured language model. It is not produced by a separately trained personal ML model. The application stores structured historical data, but it does not present ordinary LLM scoring as “personalized machine learning” before enough reliable user data and labels exist.

The interface supports English and Chinese. User data is isolated by account. The application uses SQLite locally and can connect to Supabase PostgreSQL in production.

## Memory and retrieval

The server prepares the required context for each stage deterministically: confirmed long-term profile information, facts recorded for the current day, the complete previous-day record needed for a morning review, and Python-computed statistics for weight, sleep, energy, and exercise over the previous 14 days. Core context does not depend on the model remembering to call a tool. Function calling is reserved for supplementary queries about specific dates or recent records.

When PostgreSQL/Supabase and an embedding service are configured, the server enables pgvector retrieval. Daily facts are embedded in batches and filtered by `user_id` and cutoff date. It retrieves up to 20 candidates by cosine distance, then reranks them using vector similarity (75%), recency (15%), and keyword overlap (10%). The top five historical facts are added to the model context. If embeddings are not configured, or when the app uses SQLite locally, it automatically falls back to the original SQL-based time retrieval without interrupting check-ins.

Memory is split into three layers:

- `records` stores user-submitted check-in facts only.
- `user_profiles` stores explicitly confirmed goals, available equipment, food preferences, and long-term limitations.
- `coach_outputs` stores AI guidance separately, including the model version, evidence sources, and validation results.

Legacy mixed records are migrated to this layered structure at startup. The UI shows the data sources and missing information used for each recommendation.

## Guardrails and failure handling

Model output goes through server-side structure and factual validation before it is saved. For example, when no previous-day record exists, the server forces the previous-day score to remain empty. A score can only refer to the previous day actually retrieved, and it must be between 0 and 100. Structurally incomplete answers are not written to the AI output layer.

Every submission saves the raw check-in before requesting AI guidance, so a temporary model or tool failure does not lose user data. Tool errors are returned to the model as structured results and the model receives one opportunity to correct the call. The server stops tool use after a repeated identical call, two tool errors, or four tool-call rounds, then requires a conservative answer that clearly states the information limitation.

## Behavioural evaluation

`evals/adversarial_cases.json` contains 30 failure trajectories based on known guardrail behaviours. They cover unsupported historical scores, incorrect dates, out-of-range scores, missing output fields, repeated tool calls, consecutive tool errors, and exceeding the agent step budget. These cases provide deterministic regression tests for previously fixed failure modes.

The current regression results are tracked separately as 15 automatically corrected cases, 5 rejected outputs, and 10 terminated tool loops that produce a constrained response. Because the cases were designed around existing rules and do not yet include a normal-output control group, these results are not presented as recall, accuracy, or false-positive metrics for unseen inputs, and they are not used as résumé performance claims.

Run the evaluation suite with:

```bash
python3 evals/run_adversarial_eval.py --output evals/adversarial_results.json
```

GitHub Actions runs both the unit tests and behavioural evaluation suite on every push and pull request to prevent guardrail regressions.

## Tracing, latency, and cost

Each `/api/coach` request receives a unique `traceId`. The trace records the duration and status of check-in persistence, memory construction, vector retrieval, each LLM or embedding request, tool calls, output validation, and result persistence. Traces contain stage metadata, token counts, and tool parameters, but not complete model prompts or meal photos.

When the model provider returns usage data, the system records prompt, completion, and embedding tokens. It calculates per-request cost when per-million-token rates are configured. Otherwise, cost remains `null` rather than relying on an estimated provider price.

Authenticated users can access:

- `GET /api/traces?limit=20` for recent requests and spans.
- `GET /api/metrics?limit=100` for p50/p95 latency, average and total cost, total tokens, and success rate.

The `/api/coach` response also includes an `observability` object containing the request trace ID, latency, token usage, and estimated cost.

## Run locally

There is no front-end build step. You need Python 3 and a model provider with an OpenAI-compatible Chat Completions API.

Create the local environment file:

```bash
cp .env.example .env
```

At minimum, set an API key:

```env
OPENAI_API_KEY=your_api_key
```

For Groq, use:

```env
OPENAI_API_KEY=gsk_...
OPENAI_BASE_URL=https://api.groq.com/openai/v1
OPENAI_MODEL=openai/gpt-oss-20b
```

Set `OPENAI_MODEL` to a model available to your account. When only a key beginning with `gsk_` is provided, the server also switches the request URL to Groq automatically.

To enable pgvector hybrid retrieval with Supabase, also configure:

```env
EMBEDDING_API_KEY=sk-...
EMBEDDING_BASE_URL=https://api.openai.com/v1
EMBEDDING_MODEL=text-embedding-3-small
EMBEDDING_DIMENSIONS=1536
```

At startup, the application runs `CREATE EXTENSION IF NOT EXISTS vector` and creates the `fitness_memory_chunks` table with an HNSW cosine index. The embedding dimensions must match the selected model. Changing dimensions after table creation requires a migration of the existing vector column.

To track cost, enter the current rates for your provider:

```env
MODEL_INPUT_COST_PER_1M=
MODEL_OUTPUT_COST_PER_1M=
EMBEDDING_COST_PER_1M=
```

Start the server:

```bash
python3 server.py
```

Then open <http://localhost:8000>. The interface opens the morning, post-workout, or evening stage based on local time, and users can switch stages at any time.

## Deploy to Render

The repository includes `render.yaml`. A typical production setup uses Render with Supabase:

1. Create a Supabase project and copy its PostgreSQL connection string.
2. Connect the repository to Render and create a Python Web Service.
3. Set `DATABASE_URL`, `OPENAI_API_KEY`, `OPENAI_BASE_URL`, and `OPENAI_MODEL` in Render.
4. Set `COOKIE_SECURE=true` when using HTTPS.
5. Open the Render URL after deployment and create an account.

The database tables are created when the service starts for the first time. Do not commit `.env`, API keys, or database files to GitHub.

## Data and safety boundaries

- API keys are read only by the server and are never sent to the browser.
- Passwords use PBKDF2-HMAC-SHA256, and session cookies are HttpOnly and SameSite.
- Meal photos are sent to the configured model provider, with a maximum of four images per request. Do not upload other people's faces or sensitive information.
- When vector retrieval is enabled, structured fitness records are sent to the configured embedding provider.
- AI providers enforce rate and token limits, so busy services may require a retry.
- Fitness and nutrition guidance is for general informational use and is not medical advice.
- Stop exercising and consult a qualified professional if you experience pain, chest tightness, dizziness, or other significant symptoms.

This project is still evolving through daily use. Its focus is not on producing the most polished-looking plan, but on whether the coach uses real daily evidence carefully and admits what it does not know.
